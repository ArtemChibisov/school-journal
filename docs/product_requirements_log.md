# Лог требований к продукту

Статус: рабочий черновик интервью. Файл фиксирует только подтвержденные ответы и открытые вопросы.

## Подтверждено

- В начале учебного года создаются две корневые папки отчетов: для `0-3` классов и для `4-11` классов.
- Все продуктовые папки MVP создаются и хранятся в Google Drive: папки class register, папки модулей, папки DOCX для вычитки, папки PDF для отправки и папка `Неотправленные отчеты`.
- Локальное хранилище сервера может использоваться только как временный технический буфер при генерации/конвертации файлов, но не как постоянное место хранения отчетов.
- Разделение папок связано с разной шкалой оценивания.
- По умолчанию `0-3` - начальная школа, `4-11` - средняя и старшая школа.
- Ручное переопределение шкалы для отдельного класса нужно, но это вторая волна задач.
- Завуч в начале года вносит адреса двух корневых папок.
- Внутри корневых папок есть папки модулей: `1 модуль/module`, `2 модуль/module`, ..., `6 модуль/module`, `Итоговые | Final reports`.
- Завуч запускает создание файлов по одному модулю.
- Первый модуль может быть создан и заполнен вручную завучем.
- Система должна уметь создавать следующие модули на основе первого модуля.
- При создании нового модуля копируются листы предметов, список учеников, преподаватели, структура колонок и форматирование.
- При создании нового модуля меняется номер модуля.
- При создании нового модуля очищаются оценки/уровни, комментарии, пересдачи, дескрипторы и критерии.
- Очищаются только данные, структура заполнения сохраняется.
- Лист тьютора копируется, но текст/поля, которые заполняет тьютор, очищаются.
- Если часть файлов уже создана, система сообщает об этом и предлагает выбор.
- Для существующих файлов нужны действия: пропустить существующие или заменить существующие новыми пустыми копиями.
- При замене существующие файлы можно удалять без резервной копии, но действие должно быть явным выбором завуча.
- Список классов учебного года задается завучем вручную.
- Система может просканировать папку первого модуля и подсказать найденные классы по файлам.
- Система должна показывать расхождения: класс есть в списке, но нет файла; файл есть, но класса нет в списке.
- Для создания первого модуля возможен сценарий с таблицей состава классов.
- Таблица состава классов состоит из двух листов: `classes` и `students`, связанных колонкой `class_code`. Уточнено по реальной таблице `Student_Classes`, см. `docs/data_contracts/class_roster_contract.md`.
- В таблице состава классов есть список учеников и тьютор.
- Предметы и преподаватели берутся из отдельной таблицы `класс -> предмет -> преподаватель`.
- Для таблицы предметов подходит структура: `class_code | subject_name | teacher_name`.
- Предметы могут быть на русском или английском, в зависимости от класса.
- Тип программы класса хранить не нужно для MVP.
- Предмет сохраняется ровно так, как пришел из таблицы.
- Для генерации новых class register используется один общий шаблон для всех классов.
- Преподаватели заполняют каждый свой лист в class register.
- Преподаватели добавляются в Telegram-бот, чтобы получать уведомления о заполняемости отчетов.
- Завуч видит заполняемость на платформе и в Google-таблице.
- Общий шаблон class register хранится в Google-папке.
- Общий шаблон class register правит админ, который владеет Google-папкой.
- Завуч передает системе ссылку на общий шаблон class register.
- При создании class register из общего шаблона система автоматически заполняет название класса, номер модуля, список учеников класса, тьютор, предметы и преподавателей.
- Доступ к созданным папкам и файлам получают все, кто уже имеет доступ к основной Google-папке.
- Система не управляет индивидуальными доступами к class register в MVP, а опирается на заранее выданные доступы к основной папке.
- Ученики и родители не имеют доступа к основной папке и class register.
- Google-аккаунт, от имени которого система работает с Drive/Sheets, является настройкой окружения, а не частью учебного года.
- Для локальной проверки система может работать через один Google-аккаунт, которому выданы доступы к нужным Google Drive папкам и таблицам.
- После переноса на сервер система может работать через другой Google-аккаунт или service account, если ему выданы доступы к тем же Google Drive папкам и таблицам.
- При смене окружения не нужно пересоздавать папки и файлы: нужно переавторизовать Google-доступ/заменить credentials и проверить доступность всех сохраненных ссылок.
- После создания class register система сохраняет ссылки на созданные файлы.
- Завуч видит на платформе список созданных файлов и может перейти к ним по ссылкам.
- На платформе завучу достаточно видеть статусы создания: `не создано`, `создано`, `частично создано`, `ошибка`, `есть конфликт`.
- Перед созданием файлов система проверяет, что класс есть в списке классов учебного года.
- Перед созданием файлов система проверяет, что у класса есть ученики.
- Перед созданием файлов система проверяет, что у класса есть тьютор.
- Перед созданием файлов система проверяет, что у класса есть хотя бы один предмет.
- Перед созданием файлов система проверяет, что у каждого предмета есть преподаватель.
- Если preflight-проверка нашла ошибки у части классов, система создает файлы для валидных классов.
- Проблемные классы не создаются, система сообщает завучу о причинах.
- После исправления проблем завуч подтверждает повторное создание/досоздание проблемных классов.
- Лист преподавателя считается заполненным, если заполнен текст критериев, проставлены оценки и заполнен дескриптор.
- Заполняемость листа преподавателя отображается как набор лейблов, а не как один линейный статус.
- Если работа по листу не начата, показывается статус `не начат`.
- По мере заполнения могут появляться лейблы: `заполнен дескриптор`, `написаны критерии`, `заполнены оценки`.
- Лист считается полностью заполненным, когда есть все три лейбла: дескриптор, критерии и оценки.
- Завуч вручную включает режим заполнения, когда считает нужным.
- При включении режима заполнения завуч устанавливает дедлайн по задаче, например `заполнить дескрипторы`.
- При старте режима преподавателю отправляется Telegram-сообщение о том, что пора выполнить задачу.
- В обычном режиме после стартового сообщения преподавателю отправляется одно напоминание в день в `14:00`.
- Когда начинается режим заполнения оценок, преподавателям заново отправляются сообщения о старте этой задачи.
- В режиме заполнения оценок напоминания отправляются каждый день в `10:00`, `14:00` и `18:00`.
- Если дедлайн провален, напоминания отправляются каждый день в `10:00`, `13:00`, `16:00` и `19:00`, пока задача не заполнена.
- Напоминания по конкретной задаче прекращаются, когда на листе появляется соответствующий лейбл заполнения.
- Например, по задаче `заполнить дескрипторы` напоминания прекращаются после появления лейбла `заполнен дескриптор`, даже если оценки еще не заполнены.
- В MVP завуч включает только три режима задач: `заполнить дескрипторы`, `написать критерии`, `заполнить оценки`.
- Отдельные режимы для комментариев, пересдач и тьюторского листа пока не нужны.
- Режим заполнения распространяется на текущий модуль и на все классы текущего модуля.
- В MVP не нужны точечные режимы для отдельных классов или отдельных преподавателей.
- В начале учебного года завуч устанавливает даты модулей.
- Текущий модуль определяется на основе заранее установленных дат модулей.
- При запуске режима заполнения завуч может вручную выбрать другой модуль, если фактическая работа идет не по календарному текущему модулю.
- Перед стартом учебного года завуч обязан заполнить настройки: учебный год, ссылки на две корневые папки, ссылку на общий шаблон, список классов, даты модулей, ссылку на таблицу состава классов и ссылку на таблицу `класс -> предмет -> преподаватель`.
- В мониторинге заполняемости на платформе завуч видит модуль, класс, предмет, преподавателя, ссылку на файл, лейблы заполнения, дедлайн и признак просрочки.
- Google-таблица мониторинга заполняемости повторяет те же данные, что и платформа.
- В Google-таблице одна строка соответствует одному преподавательскому листу: модуль, класс, предмет, преподаватель, ссылка на файл, лейблы заполнения, дедлайн и признак просрочки.
- Преподавателя просят добавиться в Telegram-бот для получения уведомлений.
- Сопоставление преподавателя в системе с Telegram берется из отдельной таблицы-расшифровки.
- Таблица-расшифровка Telegram содержит имя и фамилию преподавателя, а также его никнейм в Telegram.
- Если преподаватель из таблицы предметов не сопоставился с таблицей Telegram, система сообщает об этом завучу.
- В случае несовпадения завуч может поправить данные в источнике/расшифровке и повторить сопоставление.
- История Telegram-уведомлений может логироваться для администратора.
- В MVP завучу не нужен отдельный экран истории Telegram-уведомлений.
- Для администратора нужно логировать создание папок/файлов, замену файлов, ошибки генерации, ошибки сопоставления преподавателей, отправку Telegram-уведомлений и ошибки отправки.
- Пользователи платформы в MVP: завуч и администратор.
- Преподаватель в MVP работает через Google Sheets и Telegram, без отдельного входа на платформу.
- Завуч не смотрит подробные технические логи.
- Завуч не видит технические причины отказа доступов.
- Подробные логи и технические причины ошибок доступны администратору.
- Завучу достаточно показывать пользовательские ошибки: `не найден шаблон`, `не хватает данных по классу`, `не найден преподаватель в Telegram-таблице`, `файл уже существует`, `создание не удалось, обратитесь к администратору`.
- Если заполнены все преподавательские листы класса, система может формировать отчеты по этому классу.
- Готовность к формированию отчетов определяется на уровне класса, а не обязательно всего модуля.
- Завуч может запускать формирование отчетов по отдельному готовому классу.
- Завуч может запускать формирование отчетов сразу по всем готовым классам.
- Формирование отчетов идет в два этапа.
- На первом этапе система формирует DOCX-отчеты и складывает их в нужную папку по классам.
- После вычитки DOCX завуч подтверждает, что документы готовы к финализации.
- После подтверждения вычитки система пересохраняет DOCX в PDF и складывает PDF в нужную папку.
- В системе хранения есть три большие директории: таблицы с оценками по модулям, DOCX-отчеты для вычитки, PDF-отчеты, готовые к отправке.
- Исходные class register, DOCX для вычитки и финальные PDF хранятся отдельно.
- Директории DOCX-отчетов и PDF-отчетов тоже разделяются на `0-3` и `4-11`, как директории таблиц с оценками.
- Внутри директорий DOCX и PDF отчеты раскладываются по схеме `модуль -> класс -> файлы учеников`.
- DOCX/PDF файлы отчетов учеников включают модуль, класс и имя ученика.
- Если при генерации DOCX/PDF отчет с таким именем уже существует, система заменяет существующий файл новым.
- После создания PDF в MVP есть отправка отчетов родителям.
- Отправка PDF родителям не запускается автоматически после генерации PDF.
- Завуч запускает отправку родителям вручную по кнопке.
- Кнопка отправки родителям запускает отправку по всем готовым PDF.
- Контакты родителей для отправки отчетов берутся из отдельной специальной Google-таблицы.
- В таблице контактов родителей есть поля: класс/параллель, фамилия и имя ученика, почта родителя 1, почта родителя 2.
- Если у ученика заполнен только один родительский email, система отправляет отчет только на этот email.
- Если у ученика нет корректного email или отчет не ушел по почте, система сообщает об этом завучу.
- После отправки система создает документ со списком учеников/получателей, которым отчеты не ушли по почте.
- Документы со списком неотправленных отчетов хранятся в отдельной папке.
- В названии документа со списком неотправленных отчетов должны быть модуль и дата отправки.
- Документ со списком неотправленных отчетов называется `Неотправленные отчеты`.
- Документ `Неотправленные отчеты` создается в формате Google Sheet.
- В Google Sheet `Неотправленные отчеты` есть колонки: модуль, класс, ученик, email родителя 1, email родителя 2, причина, ссылка на PDF.

## Уточнения от 31.08.2026

Источник: встреча с заказчиком 31.08.2026. Разбор расхождений с ранее зафиксированными требованиями: `docs/requirements_delta_2026_08_31.md`.

Пункты этого раздела новее раздела `Подтверждено` и при противоречии имеют приоритет.

### Единый источник данных

- Входные таблицы и шаблон лежат в папке `Шаблоны` и образуют единую базу процесса.
- Таблицы связаны через класс / class key: изменение в одном месте используется во всей системе.
- Ученик имеет внутренний ID помимо ФИО, класса и grade. Формат ID требует подтверждения.
- В базе около 371 ученика.
- Принцип: одни и те же данные не дублируются в нескольких местах.

### Расписание напоминаний

Заменяет ранее зафиксированное расписание `14:00` и учащённые режимы.

- Напоминание уходит раз в день, ориентировочно в `12:00`.
- У каждого типа напоминаний есть дата начала и дата окончания рассылки.
- Дескрипторы и критерии: начало модуля, ориентировочно ко второй неделе.
- Оценки: начиная с последней недели модуля.
- Напоминания идут, пока требуемое поле не заполнено.
- Открытый вопрос: сохраняется ли учащённое расписание для режима оценок и после просрочки.

### Проверка корректности заполнения

Расширяет раздел `Заполняемость и мониторинг`: заполненность больше не сводится к трём лейблам.

- Система проверяет не факт заполнения, а корректность данных.
- Проверяются: допустимые символы и обозначения оценок, спецзначения `+` и `*`, проценты и числовые поля, обязательные поля, дескрипторы, наличие итоговых оценок.
- При обнаружении ошибки преподавателю автоматически приходит сообщение с указанием, что именно заполнено неправильно.
- Адресат сообщения об ошибке значения - преподаватель, а не только завуч.

### Таблица заполняемости

Дополняет ранее зафиксированный набор колонок.

- Нужен отдельный раздел или таблица `Заполняемость` / `Обратная связь`.
- По каждому преподавателю видно: что необходимо заполнить, что заполнено, что заполнено с ошибками, когда появилось первое заполнение, сколько напоминаний отправлено, выполнено ли требование своевременно.
- Проверка запускается фоновой задачей, ориентировочно раз в 30 минут.

### Своевременность и KPI

Новый блок требований.

- Своевременность заполнения входит в KPI преподавателя, от которого зависит 13-я зарплата.
- Хранятся два показателя: время первого действия преподавателя и количество отправленных напоминаний.
- Ориентир заказчика: 1-2 напоминания - норма, 5 напоминаний без реакции - несвоевременно.
- Цель показателя - понять, начал ли преподаватель работу вовремя, а не штрафовать за мелкие ошибки.
- Точное правило расчёта требует подтверждения.

### Отправка отчётов родителям

Заменяет ранее зафиксированный приоритет этапа.

- Целевой канал доставки - EduPage API.
- Доступ к EduPage API не получен, вопрос открыт.
- Ограничение EduPage: отправка файла может требовать уже существующей беседы с родителем.
- Этап не критичный: без автоматической отправки система имеет смысл.
- Fallback: сотрудник раз в модуль рассылает готовые PDF вручную.
- Открытый вопрос: сохраняется ли email-канал и Google Sheet `Неотправленные отчеты`.

### Приоритеты

- Главный приоритет - довести до надёжного состояния первые пять блоков: база данных, создание файлов модуля, уведомления, автоматическая проверка, таблица мониторинга.
- EduPage остаётся последним этапом.

## Основной пайплайн продукта

1. Настройка учебного года
   - Завуч задает учебный год, даты модулей, список классов, ссылки на две корневые папки `0-3` и `4-11`, ссылку на общий шаблон class register, таблицу состава классов, таблицу `класс -> предмет -> преподаватель`, таблицу Telegram-расшифровки и таблицу контактов родителей.
   - Система проверяет базовую полноту настроек и готовит учебный год к работе.

2. Создание модульной структуры и class register
   - Завуч запускает создание одного модуля.
   - Система определяет, какие классы относятся к `0-3` или `4-11`, создает/проверяет папку модуля и формирует class register на основе общего шаблона.
   - В class register автоматически заполняются название класса, номер модуля, список учеников, тьютор, предметы и преподаватели.
   - Если часть классов не проходит preflight-проверку, валидные классы создаются, а проблемные показываются завучу для исправления.

3. Работа с конфликтами создания
   - Если class register уже существует, система показывает конфликт.
   - Завуч выбирает: пропустить существующие файлы или заменить их новыми пустыми копиями.

4. Заполнение отчетов преподавателями
   - Преподаватели работают в Google Sheets, каждый в своем предметном листе.
   - Лист считается полностью заполненным, когда есть дескриптор, критерии и оценки.
   - Система отображает заполнение как лейблы: `заполнен дескриптор`, `написаны критерии`, `заполнены оценки`; если ничего нет - `не начат`.

5. Режимы заполнения и Telegram-уведомления
   - Завуч включает один из трех режимов: `заполнить дескрипторы`, `написать критерии`, `заполнить оценки`.
   - Режим применяется к текущему модулю и всем классам модуля; при необходимости завуч вручную выбирает другой модуль.
   - При старте режима преподавателям отправляется Telegram-сообщение.
   - Обычные напоминания идут раз в день в `14:00`.
   - Для режима оценок напоминания идут в `10:00`, `14:00`, `18:00`; после просрочки - в `10:00`, `13:00`, `16:00`, `19:00`.
   - Напоминания по конкретной задаче прекращаются, когда появляется соответствующий лейбл.

6. Мониторинг заполняемости
   - Завуч видит на платформе модуль, класс, предмет, преподавателя, ссылку на файл, лейблы заполнения, дедлайн и просрочку.
   - Google-таблица мониторинга повторяет эти же данные, одна строка соответствует одному преподавательскому листу.

7. Генерация DOCX-отчетов
   - Когда все преподавательские листы класса заполнены, класс готов к формированию отчетов.
   - Завуч может запустить генерацию по отдельному классу или по всем готовым классам.
   - Система формирует DOCX-отчеты и складывает их в директорию DOCX для вычитки по схеме `модуль -> класс -> файлы учеников`.
   - Файл отчета содержит в названии модуль, класс и имя ученика.

8. Подтверждение вычитки и генерация PDF
   - Завуч вычитывает DOCX и подтверждает готовность к финализации.
   - После подтверждения система конвертирует DOCX в PDF и складывает PDF в директорию готовых к отправке отчетов по схеме `модуль -> класс -> файлы учеников`.
   - Если DOCX/PDF с таким именем уже существует, система заменяет его новым.

9. Отправка PDF родителям
   - Завуч вручную запускает отправку по кнопке.
   - Кнопка отправляет все готовые PDF.
   - Контакты родителей берутся из отдельной Google-таблицы: класс/параллель, фамилия и имя ученика, почта родителя 1, почта родителя 2.
   - Если указан только один email, отчет отправляется только на него.

10. Отчет о неотправленных письмах
    - Если отчет не ушел по почте или у ученика нет корректного email, система сообщает об этом завучу.
    - Система создает Google Sheet `Неотправленные отчеты` в отдельной папке.
    - В названии документа есть модуль и дата отправки.
    - Колонки: модуль, класс, ученик, email родителя 1, email родителя 2, причина, ссылка на PDF.

## Черновик требований

### Роли и доступы

- В MVP платформа поддерживает две роли: завуч и администратор.
- Завуч работает с настройками учебного года, созданием модулей, мониторингом заполнения, запуском генерации отчетов и отправкой родителям.
- Администратор видит подробные технические логи, причины ошибок и события отправки уведомлений.
- Преподаватели не входят на платформу в MVP: они работают в Google Sheets и получают Telegram-уведомления.
- Ученики и родители не имеют доступа к папкам с class register.

- Система должна позволять завучу создать/настроить учебный год.
- Завуч должен указать ссылки на две корневые папки с class register: `0-3` и `4-11`.
- Завуч должен указать ссылки на директории DOCX-отчетов, PDF-отчетов и отчетов о неотправленных письмах.
- Завуч должен указать ссылку на общий шаблон class register.
- Завуч должен задать список классов учебного года.
- Завуч должен задать даты модулей.
- Завуч должен подключить таблицу состава классов, таблицу `класс -> предмет -> преподаватель`, Telegram-расшифровку и таблицу контактов родителей.

### Создание class register

- Система должна создавать class register для выбранного модуля на основе общего шаблона.
- Система должна заполнять название класса, номер модуля, список учеников, тьютора, предметы и преподавателей.
- Система должна уметь создавать следующий модуль на основе первого модуля.
- При копировании модуля система должна сохранять структуру листов, колонки и форматирование.
- При копировании модуля система должна очищать оценки/уровни, комментарии, пересдачи, дескрипторы, критерии и тексты тьютора.
- Система должна сохранять ссылки на созданные class register и показывать их завучу.

### Проверки и конфликты

- Перед созданием файлов система должна проверить наличие класса, учеников, тьютора, предметов и преподавателей.
- Если часть классов не проходит проверку, система должна создать валидные классы и показать завучу проблемные.
- Если файл class register уже существует, система должна предложить завучу пропустить или заменить файл.
- Если DOCX/PDF отчет уже существует, система должна заменить его новым.

### Заполняемость и мониторинг

- Система должна определять заполненность листа преподавателя по трем признакам: дескриптор, критерии, оценки.
- Система должна отображать заполняемость лейблами: `не начат`, `заполнен дескриптор`, `написаны критерии`, `заполнены оценки`.
- Система должна показывать завучу мониторинг по модулю, классу, предмету, преподавателю, ссылке на файл, лейблам, дедлайну и просрочке.
- Система должна обновлять Google-таблицу мониторинга с теми же данными, что и платформа.

### Telegram-уведомления

- Завуч должен задавать дедлайн для каждого режима.
- Режим заполнения применяется ко всем классам текущего модуля.
- Система должна отправлять преподавателям стартовое Telegram-сообщение при включении режима.
- В обычных режимах система должна напоминать один раз в день в `14:00`.
- В режиме заполнения оценок система должна напоминать в `10:00`, `14:00`, `18:00`.
- После просрочки система должна напоминать в `10:00`, `13:00`, `16:00`, `19:00`.
- Система должна прекращать напоминания по задаче после появления соответствующего лейбла.

### Генерация и отправка отчетов

- Система должна считать класс готовым к отчетам, когда заполнены все преподавательские листы класса.
- Завуч должен запускать генерацию DOCX по отдельному классу или по всем готовым классам.
- Система должна сохранять DOCX в директорию вычитки по схеме `модуль -> класс -> файлы учеников`.
- Завуч должен подтверждать вычитку DOCX перед созданием PDF.
- После подтверждения система должна конвертировать DOCX в PDF и сохранять их в директорию готовых PDF.
- Завуч должен запускать отправку родителям вручную по кнопке.
- Отправка должна идти по всем готовым PDF.
- Если отчет не отправлен, система должна создать Google Sheet `Неотправленные отчеты`.

### Данные и интеграции

- Система должна интегрироваться с Google Drive для работы с папками, шаблонами, class register, DOCX/PDF и Google Sheets.
- Система должна интегрироваться с Telegram Bot API для уведомлений преподавателей.
- Система должна использовать таблицу состава классов из двух листов `classes` и `students`, связанных колонкой `class_code`.
- Система должна использовать таблицу предметов с полями `class_code`, `subject_name`, `teacher_name`.
- Система должна хранить предметы ровно так, как они пришли из таблицы.
- Система должна использовать таблицу Telegram-расшифровки с именем, фамилией и Telegram nickname преподавателя.

### Пользовательские сообщения и логи

- Завуч должен видеть только понятные пользовательские ошибки.
- Завуч не должен видеть технические причины отказов доступа.
- Администратор должен видеть подробные логи создания файлов, замен, ошибок генерации, ошибок сопоставления, Telegram-отправок и ошибок отправки.
- Для завуча достаточно ошибок: `не найден шаблон`, `не хватает данных по классу`, `не найден преподаватель в Telegram-таблице`, `файл уже существует`, `создание не удалось, обратитесь к администратору`.

### Ограничения MVP

- Ручное переопределение шкалы оценивания для отдельного класса относится ко второй волне.
- Отдельные режимы для комментариев, пересдач и тьюторского листа в MVP не нужны.
- Индивидуальное управление доступами к class register в MVP не нужно: доступ наследуется от основной Google-папки.
- Преподавательский кабинет на платформе в MVP не нужен.

## MVP Scope

Цель MVP: дать завучу рабочий сквозной цикл модульной отчетности без ручного копирования десятков файлов и без ручного контроля заполнения.

Сквозной сценарий MVP: `настроить учебный год -> создать class register для модуля -> собрать заполнение от преподавателей -> напомнить через Telegram -> сформировать DOCX -> подтвердить вычитку -> сформировать PDF -> отправить родителям -> получить список неотправленных отчетов`.

### Входит в MVP

#### 1. Настройка учебного года

- Создание/редактирование учебного года.
- Ввод ссылок на корневые Google-папки class register для `0-3` и `4-11`.
- Ввод ссылок на директории DOCX, PDF и папку для `Неотправленные отчеты`.
- Ввод ссылки на общий шаблон class register.
- Ввод списка классов учебного года.
- Настройка дат модулей.
- Подключение Google-таблицы состава классов.
- Подключение Google-таблицы `класс -> предмет -> преподаватель`.
- Подключение Google-таблицы Telegram-расшифровки преподавателей.
- Подключение Google-таблицы контактов родителей.

#### 2. Создание class register

- Создание файлов для одного выбранного модуля.
- Автоматическое разделение классов по папкам `0-3` и `4-11`.
- Создание class register из общего шаблона.
- Автозаполнение класса, номера модуля, учеников, тьютора, предметов и преподавателей.
- Копирование следующих модулей на основе первого модуля.
- Очистка оценок/уровней, комментариев, пересдач, дескрипторов, критериев и текстов тьютора при копировании.
- Сохранение ссылок на созданные файлы.
- Отображение статусов: `не создано`, `создано`, `частично создано`, `ошибка`, `есть конфликт`.

#### 3. Preflight и конфликты

- Проверка наличия класса в списке классов.
- Проверка наличия учеников, тьютора, предметов и преподавателей.
- Частичное создание: валидные классы создаются, проблемные остаются со статусом ошибки.
- Сообщение завучу о проблемных классах.
- Повторное создание после исправления проблем.
- Обработка существующих class register: `пропустить` или `заменить`.

#### 4. Мониторинг заполнения

- Расчет лейблов заполнения: `не начат`, `заполнен дескриптор`, `написаны критерии`, `заполнены оценки`.
- Лист считается готовым, если есть дескриптор, критерии и оценки.
- Мониторинг на платформе: модуль, класс, предмет, преподаватель, ссылка на файл, лейблы, дедлайн, просрочка.
- Google-таблица мониторинга с теми же данными.

#### 5. Telegram-уведомления

- Подключение преподавателей через Telegram-бота.
- Сопоставление преподавателей по таблице Telegram-расшифровки.
- Режимы заполнения: дескрипторы, критерии, оценки.
- Ручной запуск режима завучем.
- Дедлайн для каждого режима.
- Стартовое уведомление преподавателю.
- Ежедневное напоминание в обычном режиме в `14:00`.
- Для оценок напоминания в `10:00`, `14:00`, `18:00`.
- После просрочки напоминания в `10:00`, `13:00`, `16:00`, `19:00`.
- Остановка напоминаний после появления нужного лейбла.

#### 6. Генерация DOCX

- Определение готовности класса к отчетам.
- Запуск генерации по одному готовому классу.
- Запуск генерации по всем готовым классам.
- Сохранение DOCX в директорию вычитки.
- Структура хранения: `модуль -> класс -> файлы учеников`.
- Имя файла включает модуль, класс и имя ученика.

#### 7. Подтверждение вычитки и PDF

- Ручное подтверждение завучем, что DOCX вычитаны.
- Конвертация подтвержденных DOCX в PDF.
- Сохранение PDF в директорию готовых к отправке отчетов.
- Структура хранения: `модуль -> класс -> файлы учеников`.
- Замена существующих DOCX/PDF при повторной генерации.

#### 8. Отправка родителям

- Ручной запуск отправки по кнопке.
- Отправка по всем готовым PDF.
- Получение контактов из отдельной Google-таблицы.
- Поддержка двух email родителей.
- Если заполнен один email, отправка идет на один email.
- Если отчет не отправлен, завуч получает сообщение о проблеме.

#### 9. Неотправленные отчеты

- Создание Google Sheet `Неотправленные отчеты`.
- Хранение таких документов в отдельной папке.
- Название документа содержит модуль и дату отправки.
- Колонки: модуль, класс, ученик, email родителя 1, email родителя 2, причина, ссылка на PDF.

#### 10. Административные логи

- Логирование создания папок и файлов.
- Логирование замен файлов.
- Логирование ошибок генерации.
- Логирование ошибок сопоставления преподавателей.
- Логирование отправки Telegram-уведомлений и ошибок отправки.
- Логирование отправки родительских отчетов.

### Не входит в MVP

- Кабинет преподавателя на платформе.
- Кабинет родителя или ученика.
- Индивидуальная раздача доступов к class register.
- Ручное переопределение шкалы оценивания для отдельного класса.
- Отдельные режимы заполнения для комментариев, пересдач и тьюторского листа.
- Автоматическая отправка родителям сразу после PDF-генерации.
- Продвинутые дашборды, графики и аналитика.
- Автоматическое исправление несовпадений ФИО преподавателей или учеников.
- Версионирование/резервные копии заменяемых файлов.
- Сложный approval-flow для нескольких проверяющих DOCX.

### Критерии готовности MVP

- Завуч может полностью настроить учебный год через платформу.
- Система создает class register для выбранного модуля по всем валидным классам.
- Завуч видит понятные ошибки по невалидным классам.
- Преподаватели получают Telegram-уведомления и напоминания по активным режимам.
- Завуч видит заполненность на платформе и в Google-таблице.
- Система формирует DOCX по готовым классам.
- Завуч может подтвердить вычитку и получить PDF.
- Отправка родителям вынесена за пределы критериев готовности MVP решением заказчика от 31.08.2026. Конечная точка обязательного контура - готовые PDF в папке модуля. См. `docs/requirements_delta_2026_08_31.md`.
- Система создает Google Sheet `Неотправленные отчеты`, если часть отчетов не ушла.
- Администратор видит технические логи, а завуч не видит технические причины отказов доступа.

### Главный результат MVP

Школа может пройти один полный модульный цикл отчетности от создания файлов до отправки PDF родителям, а завуч контролирует процесс без ручного поиска незаполненных листов и ручной рассылки напоминаний.

- Завуч может указать таблицу контактов родителей.
- Система проверяет, что ссылки заполнены.
- Если таблица недоступна или не читается, завуч видит понятную ошибку.

### US-03. Проверить классы перед созданием модуля

Как завуч, я хочу перед созданием модуля видеть проблемы в исходных данных, чтобы исправить их до появления неполных файлов.

Acceptance Criteria:
- Система проверяет, что класс есть в списке классов учебного года.
- Система проверяет наличие учеников, тьютора, предметов и преподавателей.
- Система показывает список валидных и проблемных классов.
- Для проблемных классов завуч видит понятную причину.
- Валидные классы могут быть созданы даже при наличии проблемных классов.

### US-04. Создать class register для модуля

Как завуч, я хочу создать class register для выбранного модуля, чтобы не копировать и не готовить файлы вручную.

Acceptance Criteria:
- Завуч выбирает учебный год и модуль.
- Система создает class register на основе общего шаблона.
- Система автоматически заполняет класс, номер модуля, учеников, тьютора, предметы и преподавателей.
- Файлы создаются в правильной папке `0-3` или `4-11`.
- Система сохраняет ссылки на созданные файлы.
- Завуч видит статус создания по каждому классу.

### US-05. Обработать конфликт существующего class register

Как завуч, я хочу выбрать действие для уже существующих class register, чтобы случайно не потерять нужные данные.

Acceptance Criteria:
- Система заранее показывает, какие файлы уже существуют.
- Завуч может выбрать `пропустить`.
- Завуч может выбрать `заменить`.
- При `пропустить` система создает только отсутствующие файлы.
- При `заменить` система создает новую пустую копию вместо существующего файла.
- Результат операции отображается в статусах создания.

### US-06. Создать следующий модуль на основе первого

Как завуч, я хочу создавать следующие модули на основе первого, чтобы сохранять структуру файлов и не переносить данные вручную.

Acceptance Criteria:
- Система копирует листы предметов, учеников, преподавателей, структуру колонок и форматирование.
- Система меняет номер модуля.
- Система очищает оценки/уровни, комментарии, пересдачи, дескрипторы и критерии.
- Система очищает текстовые поля тьютора, которые должны быть заполнены заново.
- Структура заполнения не ломается.

### US-07. Смотреть список созданных файлов

Как завуч, я хочу видеть созданные class register на платформе, чтобы быстро переходить к нужным Google Sheets.

Acceptance Criteria:
- Завуч видит учебный год, модуль, класс и ссылку на class register.
- Завуч видит статус файла: `не создано`, `создано`, `частично создано`, `ошибка`, `есть конфликт`.
- Ссылка открывает соответствующий Google Sheet.
- Если файл не создан, ссылка не показывается.

### US-08. Видеть заполняемость преподавательских листов

Как завуч, я хочу видеть заполняемость по каждому преподавательскому листу, чтобы понимать, кто уже готов, а кому нужно напомнить.

Acceptance Criteria:
- Завуч видит модуль, класс, предмет, преподавателя и ссылку на файл.
- Система показывает лейблы `заполнен дескриптор`, `написаны критерии`, `заполнены оценки`.
- Если ничего не заполнено, система показывает `не начат`.
- Лист считается готовым, если есть все три лейбла.
- Завуч видит дедлайн и признак просрочки.

### US-09. Обновлять Google-таблицу мониторинга

Как завуч, я хочу видеть мониторинг заполнения в Google-таблице, чтобы работать с теми же данными вне платформы.

Acceptance Criteria:
- Система создает или обновляет Google-таблицу мониторинга.
- Одна строка соответствует одному преподавательскому листу.
- В строке есть модуль, класс, предмет, преподаватель, ссылка на файл, лейблы, дедлайн и просрочка.
- Данные в Google-таблице соответствуют данным на платформе.

### US-10. Включить режим заполнения

Как завуч, я хочу включать режим заполнения по текущему модулю, чтобы преподаватели получили понятную задачу и дедлайн.

Acceptance Criteria:
- Завуч выбирает один из режимов: дескрипторы, критерии, оценки.
- Завуч задает дедлайн.
- По умолчанию режим применяется к текущему модулю.
- Завуч может вручную выбрать другой модуль.
- Режим применяется ко всем классам выбранного модуля.
- После запуска преподавателям отправляется стартовое Telegram-сообщение.

### US-11. Получать Telegram-напоминания

Как преподаватель, я хочу получать Telegram-напоминания о незаполненных задачах, чтобы не пропустить дедлайн.

Acceptance Criteria:
- Преподаватель получает стартовое сообщение при запуске режима.
- В обычном режиме напоминание приходит ежедневно в `14:00`.
- В режиме оценок напоминания приходят в `10:00`, `14:00`, `18:00`.
- После просрочки напоминания приходят в `10:00`, `13:00`, `16:00`, `19:00`.
- Напоминания по задаче прекращаются, когда появляется соответствующий лейбл.

### US-12. Сопоставить преподавателей с Telegram

Как завуч, я хочу видеть несопоставленных преподавателей, чтобы исправить Telegram-расшифровку и обеспечить уведомления.

Acceptance Criteria:
- Система использует таблицу с именем, фамилией и Telegram nickname.
- Если преподаватель не найден в Telegram-таблице, система показывает проблему завучу.
- Завуч может исправить данные в источнике и повторить сопоставление.
- Технические детали ошибки доступны администратору в логах.

### US-13. Сформировать DOCX по готовому классу

Как завуч, я хочу сформировать DOCX-отчеты по готовому классу, чтобы начать вычитку отчетов.

Acceptance Criteria:
- Класс считается готовым, когда все преподавательские листы класса заполнены.
- Завуч может запустить генерацию по одному готовому классу.
- Система создает DOCX для учеников класса.
- DOCX сохраняются в директорию вычитки по схеме `модуль -> класс -> файлы учеников`.
- Имя файла содержит модуль, класс и имя ученика.

### US-14. Сформировать DOCX по всем готовым классам

Как завуч, я хочу сформировать DOCX сразу по всем готовым классам, чтобы не запускать генерацию много раз вручную.

Acceptance Criteria:
- Завуч может запустить генерацию по всем готовым классам.
- Система пропускает неготовые классы.
- По каждому классу система показывает результат генерации.
- Существующие DOCX с тем же именем заменяются.

### US-15. Подтвердить вычитку DOCX

Как завуч, я хочу подтверждать вычитку DOCX, чтобы PDF создавались только из проверенных документов.

Acceptance Criteria:
- Завуч видит классы/пакеты DOCX, ожидающие подтверждения.
- Завуч может подтвердить готовность DOCX к PDF.
- Без подтверждения PDF не создаются.
- Подтверждение фиксируется в системе.

### US-16. Сформировать PDF

Как завуч, я хочу после подтверждения вычитки сформировать PDF, чтобы подготовить отчеты к отправке родителям.

Acceptance Criteria:
- Система конвертирует подтвержденные DOCX в PDF.
- PDF сохраняются в директорию готовых отчетов по схеме `модуль -> класс -> файлы учеников`.
- Имя PDF содержит модуль, класс и имя ученика.
- Существующие PDF с тем же именем заменяются.
- Завуч видит результат PDF-генерации.

### US-17. Отправить готовые PDF родителям

Как завуч, я хочу отправить все готовые PDF родителям одной кнопкой, чтобы завершить модульную отчетность без ручной рассылки.

Acceptance Criteria:
- Отправка не стартует автоматически после PDF-генерации.
- Завуч запускает отправку вручную по кнопке.
- Система отправляет все готовые PDF.
- Контакты родителей берутся из специальной Google-таблицы.
- Если у ученика один email родителя, отправка идет на один email.
- Результат отправки фиксируется в системе.

### US-18. Получить список неотправленных отчетов

Как завуч, я хочу получить список отчетов, которые не ушли родителям, чтобы быстро исправить контакты или отправить вручную.

Acceptance Criteria:
- Если отчет не ушел, система сообщает об этом завучу.
- Система создает Google Sheet `Неотправленные отчеты`.
- Документ хранится в отдельной папке.
- Название содержит модуль и дату отправки.
- В таблице есть модуль, класс, ученик, email родителя 1, email родителя 2, причина и ссылка на PDF.

### US-19. Видеть понятные ошибки

Как завуч, я хочу видеть ошибки простым языком, чтобы понимать, что нужно исправить без технических деталей.

Acceptance Criteria:
- Завуч видит ошибки: `не найден шаблон`, `не хватает данных по классу`, `не найден преподаватель в Telegram-таблице`, `файл уже существует`, `создание не удалось, обратитесь к администратору`.
- Завуч не видит технические причины отказа доступов.
- Подробные причины доступны администратору.

### US-20. Смотреть административные логи

Как администратор, я хочу видеть подробные логи операций, чтобы диагностировать ошибки интеграций и генерации.

Acceptance Criteria:
- Администратор видит создание папок и файлов.
- Администратор видит замены файлов.
- Администратор видит ошибки генерации.
- Администратор видит ошибки сопоставления преподавателей.
- Администратор видит отправку Telegram-уведомлений и ошибки отправки.
- Администратор видит отправку родительских отчетов и ошибки отправки.
