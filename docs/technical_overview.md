## 1. Что система делает

Школа ведёт журналы в Google-таблицах: один файл на класс, один лист на предмет. Преподаватели
заполняют дескрипторы, критерии оценивания и оценки учеников.

Система:

1. читает эти журналы и показывает, что не заполнено;
2. проверяет, что оценки записаны так, как отчёт сумеет прочитать;
3. напоминает преподавателям о незаполненном через Telegram;
4. собирает из журналов отчёты по каждому ученику в DOCX и PDF;
5. отправляет отчёты родителям.

Сама она журналы **не создаёт** — пока только находит созданные вручную. Генерация запланирована,
см. очередь 3 в рабочем плане.

## 2. Из чего собрана

Django 5, один процесс, PostgreSQL. Разворачивается в Docker Compose за системным Caddy.

| Приложение | За что отвечает |
| --- | --- |
| `school_years` | Учебный год, модули, классы, преподаватели, предметы. Импорт входных таблиц |
| `google_integration` | Доступ к Google: Drive, Sheets, разбор ссылок, понятные тексты ошибок |
| `journal_links` | Связки «класс → таблица журнала». Проверка значений оценок |
| `validation` | Проверка заполненности журналов, выгрузка мониторинга |
| `pipeline` | Критерии, AI-вычитка, сборка DOCX и PDF, отправка родителям |
| `notifications` | Telegram: приглашения, напоминания, подтверждения |
| `jobs` | Запуски и журнал событий |
| `webapp` | Общий шаблон, меню, стили |
| `admin_panel` | Настройки, карта адресов, проверки живости |
| `school_journal-main` | Код до переезда в Django. Используется для сборки DOCX |

### Почему легаси остаётся

`school_journal-main/` — скрипты, которыми школа пользовалась до появления панели. Сборка DOCX
до сих пор идёт через них: `pipeline/legacy_docx.py` подгружает их как модули и вызывает.

Переписывать их не стали намеренно. Они дают отчёт, который школа уже считает правильным, а
любая переделка — это риск получить другой документ без возможности заметить разницу.

Там же лежат правила оценивания — два словаря шкал, `marks_dict.py` для классов 0–3 и
`marks_dict_upd.py` для 4–11. Их читают и легаси-сборщик, и новая проверка значений, чтобы
проверка предсказывала поведение отчёта, а не спорила с ним.

## 3. Доменная модель

```
SchoolYear ──┬── SchoolModule ──── ClassRegister
             ├── ClassGroup ─────── SubjectTeacher ─── Teacher
             └── Teacher
```

| Модель | Что хранит |
| --- | --- |
| `SchoolYear` | Учебный год и **13 ссылок** на таблицы и папки Google |
| `SchoolModule` | Даты модуля и шесть папок: журналы, DOCX, PDF — для 0–3 и 4–11 |
| `ClassGroup` | Класс: код, номер параллели, тьютор. Импортируется из таблицы состава |
| `Teacher` | Преподаватель: **два написания имени**, русское и английское |
| `SubjectTeacher` | Кто какой предмет ведёт в каком классе |
| `ClassRegister` | Журнал класса в модуле: ссылка на таблицу и статус |
| `TeacherSheetStatus` | Состояние листа преподавателя. Пока не используется |
| `ReportArtifact` | Сгенерированный документ |

### Про два написания имени

Школа называет преподавателя на языке, на котором идёт обучение в классе: `Юлия Галкина` в
классах «А», `Yuliya Galkina` в классах «К». В журнале ничего не говорит, что это один человек.

Без справочника система считала бы их двумя: в таблице мониторинга человек двоится, а
напоминание уходит на имя, за которым никого нет.

Альтернативой был перевод журналов на одно написание — около 120 листов правок, с промежуточным
состоянием, где человек раздваивается внутри одного журнала. Справочник решает ту же задачу,
не трогая журналы.

### Мост к старому слою

`journal_links.ClassSheetLink` — связка «класс → таблица». От неё работают проверка
заполненности, AI-вычитка, таблица критериев и генерация DOCX: пятнадцать файлов.

Поэтому подхват журналов пишет не только в `ClassRegister`, но и в `ClassSheetLink`. То же со
ссылкой на таблицу мониторинга: экран «Учебный год» владеет ею, а при сохранении обновляет
старую настройку `DescriptorCriteriaReportTarget`.

Это мосты, а не архитектура. Когда мониторинг переедет на доменную модель, их можно убрать.

### Ученик

`Student` — ученик класса, из листа `students`. Лист читался и проверялся с самого начала, но
до недавнего времени не сохранялся: система знала, что учеников 367, и не знала ни одного по
имени, поэтому создавать журнал было не из чего.

Имя хранится целиком, как в таблице. Делить его на имя и фамилию — задача того места, где это
нужно: фамилии бывают двойными, и одна неверная догадка размножается по всем отчётам.

Ушедший из таблицы отключается, а не удаляется: отчёт за прошлый модуль всё ещё о нём.

## 4. Входные данные

Всё, что система знает о школе, приходит из Google-таблиц. Ссылки задаются на экране
«Учебный год», форматы описаны в [data_contracts/](data_contracts/).

| Таблица | Листы | Что даёт |
| --- | --- | --- |
| Состав классов | `classes`, `students` | Классы, тьюторы, ученики |
| Предметы и преподаватели | `subject_teachers`, `teachers` | Кто что ведёт, справочник имён |
| Бланк журнала 0-3 | `Предмет1` | Образец листа предмета для младших классов |
| Бланк журнала 4-11 | `Предмет1`, `Тьютор \| Tutor` | То же для остальных, плюс лист тьютора |
| Контакты родителей | `parent_contacts` | Кому отправлять отчёты |
| Мониторинг заполняемости | — | Куда выгружать отчёт |

Бланков два, потому что половины школы оценивают по разным шкалам. Выбирается по параллели
класса из состава классов: по коду класса такое не определить, он просто текст.

Папки Drive: журналы, DOCX и PDF — отдельно для 0–3 и 4–11.

### Доступ к Google

Режим `oauth_owner`: система действует от имени одного аккаунта школы. Токен с `refresh_token`
лежит в `/app/creds/google/rt.json`, `client_secret.json` рядом.

Важное свойство: если в Google Cloud у проекта **Publishing status = Testing**, Google убивает
refresh-токены через 7 дней, и система молча перестаёт видеть журналы. Вопрос открыт.

**Чьи это файлы.** Всё, что система создаёт — папки модулей и классов, журналы, DOCX, PDF, —
принадлежит аккаунту из токена, в какую бы папку школы оно ни легло. Оно занимает его квоту, и
удаление у него удаляет файл у школы. Смена токена ничего не переносит. Перенос — команда
`transfer_drive_ownership` (`google_integration/ownership.py`): между личными аккаунтами Google
передаёт владение в два шага — `offer` с токеном старого аккаунта, `accept` с токеном нового.
Обходятся все ссылки из учебных лет, модулей и журналов вглубь, трогается только то, чем владеет
старый аккаунт; без `--apply` команда только показывает, что сделает.

## 4а. Создание журналов модуля

Раньше это была ручная работа: завуч заводил папку модуля, вставлял две ссылки в настройки
модуля и копировал бланк по разу на класс, в каждой копии размножая лист по предметам.

Теперь это кнопка на экране «Журналы модуля», `school_years/register_generation.py`:

```
Журналы 0-3            указано в настройках года
└── 1 модуль/module    создаётся системой, адрес пишется обратно в модуль
    └── 2Б 1 модуль    копия бланка
        ├── Математика   лист на предмет, C1 класс, C2 учитель, C3 модуль
        ├── Чтение
        └── Тьютор | Tutor   только у 4-11
```

Листы множатся через `duplicateSheet`, а не создаются заново: выпадающие списки в бланке —
это и есть бланк, учитель выбирает уровень из них. Образец `Предмет1` удаляется последним.

**Привязка — часть генерации.** Созданный файл записывается в `ClassRegister` и в
`ClassSheetLink`. Пока журнал не привязан, его не видит ничто: ни проверка заполнения, ни
проверка оценок, ни сборка отчётов. Раньше это делал отдельный поиск по папкам, и забыть его
нажать было легко; поиск остался для журналов, сделанных вручную.

Класс, у которого нет предметов или бланка, пропускается с причиной — остальные создаются.
Уже существующий журнал не трогается: в нём может быть работа преподавателей.

## 5. Как читается журнал

Самая тонкая часть системы — здесь легко получить неверный ответ, не заметив этого.

### Скачивание

Журнал скачивается как `.xlsx` по адресу вида
`https://docs.google.com/spreadsheets/d/{id}/export?format=xlsx` и читается через `openpyxl`.

**Excel не держит имя листа длиннее 31 символа**, и Google обрезает его при экспорте. Поэтому
настоящие имена листов берутся отдельным запросом к Sheets API и подставляются по порядку.
Сопоставление принимается, только если число листов совпало и короткое имя является началом
длинного: Excel ещё и заменяет символы, которые не принимает, и неверная догадка переименовала
бы не тот предмет.

Если имена получить не удалось — проверка не падает, пишет предупреждение в журнал событий и
идёт дальше с короткими именами. Журнал уже скачан и читается; отменять разбор из-за написания
названия неправильно.

### Структура листа

Якоря ищутся по тексту, а не по координатам:

```
Класс | Grade                    → код класса справа
Учитель | Teacher                → имя преподавателя справа
Учебный модуль # | Module #      → номер модуля
Дескриптор | Descriptor          → текст дескриптора
Критерии оценивания | Assessment criteria → заголовки критериев правее
```

Критерии заканчиваются на первой **служебной колонке**: «Комментарий», «Пересдача», `retake`,
`resit`, `make-up`. «Пересдача» содержит `да`/`нет` — это не оценка, и отчёт читает её отдельно,
чтобы подсветить комментарий преподавателя.

Листы с именами тьюторского и служебного типа пропускаются.

### Значения оценок

Правила перенесены из `enrich_mark` в легаси и из рендера отчёта. Ячейка понимается, если в ней:

- **текст уровня шкалы** — так заполнено 19 тысяч оценок из 19 с небольшим тысяч;
- **число**, попадающее в диапазон `low < значение <= high`. Запятая и точка равноправны;
- **прочерк** любого вида: `-`, `--`, `–`, `—`, `−`, пробелы. Значит «оценки нет»;
- **буква с числом**: `86, A`, `70 - B`. Рендер достаёт букву и печатает `86% A`.

Всё остальное отчёт теряет молча. Экран «Проверка оценок» показывает такие значения заранее.

Одно место, где проверка строже рендера: тот ищет букву в чём угодно, и в предложении со словом
`a` найдёт оценку `A`. Поэтому ячейка проходит, только если **каждое слово** в ней — часть
оценки. Подменённая оценка хуже потерянной.

## 6. Задачи и журнал событий

Всё, что система делает долго, оформлено как `JobRun` с записями `JobLog`. Экран «Журнал
событий» (`/logs/`) показывает их одним потоком по всем запускам.

| Тип | Что делает |
| --- | --- |
| `class_roster_import` | Импорт состава классов |
| `subject_teacher_import` | Импорт предметов, преподавателей и справочника |
| `class_register_scan` | Поиск журналов модуля в папках и привязка к классам |
| `descriptor_criteria_fill_check` | Проверка заполненности |
| `grade_value_check` | Проверка значений оценок |
| `module_review_reports` | Сборка DOCX по модулю |
| `prepare_student_review_reports` | Сборка DOCX по одному классу |
| `descriptor_fill_reminders` | Напоминания преподавателям |
| `google_access_preflight` | Проверка доступа ко всем ссылкам года |
| `run_full_pipeline` | Полный проход: дескрипторы → критерии → DOCX → PDF → родителям |

Правило отчётов: **одна плохая строка не блокирует остальные**. Класс с ошибкой пропускается по
имени, с причиной, остальные обрабатываются. Импортировать половину класса хуже, чем пропустить
его целиком: генерация потом отработает на классе, который выглядит полным.

## 7. Сборка отчётов

```
Журнал класса (Google Sheets)
      ↓ скачать .xlsx
Легаси-сборщик → DOCX на каждого ученика
      ↓
DOCX 0-3 / 1 модуль/module / 1А / Иванов.docx
```

Папка верхнего уровня берётся из настроек модуля, а если там пусто — из настроек года. Папку
модуля и папку класса система создаёт сама, предварительно проверив, нет ли их: Drive спокойно
держит две папки с одинаковым именем рядом, и повторный запуск построил бы вторую ветку.

**Доступ.** Папку, которую создал сервис, видит только сервис — он её владелец. Завуч открывала
отчёт по ссылке из панели и получала от Google «You need access» на собственные отчёты школы.
Поэтому папка модуля открывается адресу из поля «Доступ к отчётам» в настройках года — один раз
за запуск, а папки классов и сами файлы наследуют доступ. Права, выставленные руками, не трогаются:
школа могла сознательно дать кому-то только чтение. Если поле пустое или Google отказал, запуск
пишет предупреждение в журнал и продолжает: отчёты, которым не хватает одной выдачи прав, лучше,
чем отсутствие отчётов.

**Повторный запуск.** Это штатный способ починить класс. Отчёт перезаписывается по имени
файла и сохраняет свой id — ссылка, которую завуч уже кому-то отправила, открывает исправленную
версию. Чего повторный запуск сделать не может — убрать отчёт, который он больше не собирает:
исправленная в журнале фамилия даёт новый файл, а старый остаётся рядом, и оба выглядят
настоящими. Такие файлы система считает, называет в таблице классов и пишет в журнал событий,
а удаляет только если на форме поставили галку — тогда они уходят в корзину Drive, откуда их
можно вернуть 30 дней. Если класс собрать не удалось, сравнение не делается вовсе: собрано
ничего, и тогда любой файл в папке — чей-то настоящий отчёт.

**PDF.** Это отдельный второй шаг, а не часть сборки. Отчёты уже лежат в Drive, поэтому ничего
не скачивается и никакой конвертер на сервер не ставится: DOCX копируется как Google Doc,
копия экспортируется в PDF, байты кладутся в папку PDF, копия удаляется. Дерево папок
такое же, на корень левее — `PDF 0-3 / 1 модуль/module / 4А`.

Источник PDF — это **содержимое папки класса в DOCX**, а не результат последнего запуска.
Отсюда два следствия: журналы при этом не читаются, так что исправленный журнал без пересборки
DOCX в PDF не попадёт; и лишние DOCX, оставшиеся от прошлых запусков, тоже станут PDF, пока их
не убрали галкой.

Поэтому у шага своя страница, `/module-pdf/`, и на ней сначала **проверка**: она обходит те же
папки и говорит по каждому классу, сколько там DOCX, сколько уже PDF и какая из причин мешает,
если сохранять нечего. Проверка ничего не создаёт — класс, у которого папки ещё нет, это класс
без отчётов, а не класс, которому нужна папка. По той же причине и сам запуск сначала смотрит,
есть ли что конвертировать, и только потом создаёт папку назначения: иначе нажатие не в том
порядке засоряло оба корня пустыми папками.

Шкала оценок выбирается по параллели класса из состава классов: 0–3 и 4–11 читают разные
словари и получают разные подписи колонок.

Классы обрабатываются по очереди. Каждый скачивает журнал и загружает файл на ученика;
тридцать два таких процесса разом упрутся в ограничения Google и не скажут, какой класс упал.

## 8. Telegram

Бот решает две задачи: регистрация преподавателей и напоминания.

**Регистрация.** Система не знает ника преподавателя и не нуждается в нём — нужен `chat_id`, а
его Telegram сообщает сам, когда человек нажимает Start. Экран «Приглашения в Telegram» выдаёт
персональную ссылку с одноразовым токеном; бот по токену понимает, чей чат получил.

**Напоминания.** Строятся по последней проверке заполненности, группируются по преподавателю.
Завуч может снять галку — тогда напоминания этому человеку не уходят **в текущем модуле**.

Выключение привязано к модулю намеренно. Преподаватель Drama написал в дескрипторе, что в
первом модуле сознательно не проводил критериальное оценивание и введёт критерии во втором;
молчание должно закончиться вместе с модулем, а не ждать, пока кто-то вспомнит включить его
обратно.

Имя из журнала сопоставляется с человеком через справочник, поэтому одна галка гасит оба
написания.

## 9. Экраны

Экраны сгруппированы в четыре раздела, описанные один раз в `webapp/navigation.py`: оттуда
рисуются и боковое меню, и главная, и страницы разделов. Второй копии списка нет намеренно —
список, который ведут руками в трёх шаблонах, расходится на первой правке.

| Адрес | Экран | Раздел |
| --- | --- | --- |
| `/` | Главная: разделы и документация | — |
| `/docs/product/`, `/docs/technical/` | Документация, из `docs/*.md` | — |
| `/links/fill-check-report/` | Отчёт заполненности | Работа с модулем |
| `/reminders/`, `/reminders/invites/` | Напоминания и приглашения в Telegram | Работа с модулем |
| `/links/grade-values/` | Проверка оценок | Работа с модулем |
| `/criteria-table/` | Таблица критериев | Работа с модулем |
| `/student-review-reports/` | Отчёты на проверку (DOCX) | Работа с модулем |
| `/module-pdf/` | Сохранение в PDF | Работа с модулем |
| `/parent-reports/` | Рассылка родителям | Работа с модулем |
| `/school-year/` | Учебный год | Настройки года |
| `/roster/` | Состав классов | Настройки года |
| `/subject-teachers/` | Предметы и преподаватели | Настройки года |
| `/assistant-principals/` | Завучи | Настройки года |
| `/links/` | Классы и таблицы | Настройки года |
| `/modules/` | Журналы модуля: даты и «Завести журналы» | Настройки года |
| `/parent-contacts/` | Контакты родителей | Настройки года |
| `/parent-mail/` | Почта для родителей и текст письма | Настройки года |
| `/runs/`, `/logs/` | Запуски и журнал событий | Служебное |
| `/google/status/` | Google-подключение | Служебное |
| `/system/` | Состояние системы | Служебное |
| `/healthz`, `/readyz` | Проверки живости, для внешнего монитора | — |
| `/ai-criteria-review/`, `/criteria-failures/`, `/valid-criteria/` | AI-вычитка: из меню убраны | — |

`/system/` отвечает на вопрос «всё ли работает» в одном месте: база, учебный год, Google,
почта, Telegram, завучи и сбои за сутки. Наружу не ходит — открытие страницы не должно тратить
квоту Google и тем более что-то отправлять.

Правило: **фаза считается законченной, когда результат виден в браузере**, а не только в выводе
команды.

только панелью.

## 11. Развёртывание

Отправка в `main` автоматически обновляет боевой сервер — отдельной команды деплоя нет.

```
GitHub Actions → ssh → git pull → docker compose up -d --build → health check
```

Миграции применяются при старте контейнера `web`. У `scheduler` они отключены, чтобы два
контейнера не мигрировали одновременно.

Приложение слушает `127.0.0.1:8090`, наружу пускает системный Caddy. На том же сервере работают
Moodle, Nextcloud и другие сервисы школы — порты 80 и 443 занимать нельзя.

Автопроверка заполненности идёт по расписанию в отдельном контейнере `scheduler`.

## 12. Что намеренно не сделано

**У ученика нет внутреннего идентификатора.** Ученики хранятся, но опознаются по классу и
имени: формат идентификатора школа не называла. Пока в одном классе нет тёзок, это работает;
появятся — различать их будет нечем.

**AI-вычитка критериев выключена.** Страницы остались и открываются по прямой ссылке, но из
меню убраны, а уведомления преподавателям по её выводам отправить нельзя: сообщение состояло
из вердикта модели и её подсказки, и отправлять такое от имени школы — значит выдавать мнение
модели за требование завуча.

**Старый полный прогон выключен.** Он собирал отчёты из файлов на диске — без модуля, дат,
года и завуча — и рассылал их родителям. Пока почта не была настроена, он упирался в SMTP;
после настройки он разослал бы всем семьям отчёты с пустой шапкой. Код ещё лежит:
`full_pipeline_runner`, `docx_job_runner`, `services_pdf`, `parent_reports_job_runner`,
`services_parent_reports` — кнопок на них нет, маршруты отказывают.

**Критерии не помечаются как неприменимые.** Там, где критериальное оценивание не проводится,
отчёт показывает проблему. Обходится выключением напоминаний на модуль.

**Email родителям и EduPage.** Отправка отчётов пока только через email; интеграции с EduPage
нет, доступ к API не получен.
