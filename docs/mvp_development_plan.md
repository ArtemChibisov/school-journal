# План разработки MVP системы отчетности

Статус: черновик для команды разработки.

Источник требований: `docs/product_requirements_log.md`.

Цель документа: превратить собранные требования, MVP Scope и User Stories в этапы разработки и конкретные инженерные задачи.

## 1. Цель MVP

MVP должен провести школу через один полный модульный цикл отчетности:

`настройка учебного года -> создание class register -> мониторинг заполнения -> Telegram-напоминания -> DOCX для вычитки -> PDF -> отправка родителям -> отчет о неотправленных письмах`.

Главная ценность MVP: завуч перестает вручную копировать десятки файлов, вручную искать незаполненные листы и вручную напоминать преподавателям.

Ключевое правило хранения: все постоянные продуктовые папки MVP находятся в Google Drive. Это касается папок class register, папок модулей, DOCX-директорий для вычитки, PDF-директорий для отправки и папки `Неотправленные отчеты`. Локальная файловая система сервера может использоваться только как временный буфер для генерации или конвертации файлов.

Ключевое правило авторизации Google: Google-аккаунт системы является настройкой окружения. Локально проект может работать через один OAuth-аккаунт, а на сервере через другой OAuth-аккаунт или service account. Продуктовые настройки учебного года должны хранить ссылки/ID папок и таблиц, но не должны быть привязаны к конкретному локальному токену.

## 2. Текущая техническая база проекта

Проект уже содержит части, которые нужно переиспользовать:

- `jobs`: `JobRun` и `JobLog` для запуска и логирования долгих операций.
- `journal_links`: ссылки на Google Sheets и отчеты по заполненности дескрипторов/критериев.
- `validation`: проверки заполненности и команды мониторинга.
- `notifications`: контакты преподавателей, Telegram-уведомления, события уведомлений.
- `pipeline`: DOCX/PDF/report pipeline, parent contacts, отправка родительских отчетов.
- `school_journal-main`: legacy-слой генерации DOCX, который уже используется через адаптер.

Важно: MVP лучше строить как развитие существующего Django-проекта `admin_panel`, а не как отдельную систему.

## 3. Рекомендуемая архитектура MVP

### 3.1 Новый доменный слой

Добавить новый Django app, например `school_years`, для сущностей учебного года и модульной структуры.

Причина: текущие приложения уже отвечают за конкретные части пайплайна, но нет центральной модели учебного года, модулей, классов и директорий.

### 3.2 Переиспользуемые приложения

- `jobs`: все долгие операции оформлять как `JobRun`.
- `notifications`: расширять для новых режимов заполнения и Telegram-рассылок.
- `pipeline`: расширять для DOCX/PDF/parent sending.
- `journal_links` или новый сервис мониторинга: использовать для ссылок на class register и заполненности.

### 3.3 Интеграции

- Google Drive API: папки, копирование шаблонов, размещение DOCX/PDF.
- Google Sheets API: чтение входных таблиц, запись мониторинга, создание `Неотправленные отчеты`.
- Telegram Bot API: уведомления преподавателям.
- Email backend: отправка PDF родителям.

Google-доступ:
- локально использовать `GOOGLE_ACCESS_MODE=oauth_owner` и OAuth-токен аккаунта, которому выдан доступ к тестовым/рабочим папкам;
- на сервере использовать отдельный production OAuth-аккаунт или `GOOGLE_ACCESS_MODE=service_account`;
- при переносе окружения повторно проходить Google-авторизацию или заменять service account credentials;
- после смены аккаунта запускать проверку доступов ко всем сохраненным папкам, таблицам и шаблону.

Имена моделей можно уточнить при реализации, но данные нужны именно такие.

Хранит настройки учебного года.

Поля:

- `is_active`.
- `register_root_0_3_url`.
- `register_root_4_11_url`.
- `docx_root_0_3_url`.
- `docx_root_4_11_url`.

- `monitoring_sheet_url`.

## 4A. Изменения моделей по итогам встречи 31.08.2026

Источник: `docs/requirements_delta_2026_08_31.md`. Эти изменения дополняют раздел 4 и имеют приоритет над ним.

### 4A.1 Новая модель `Student`

Причина: заказчик требует внутренний ID ученика. Сейчас отчёты привязаны к имени строкой, что ломается при однофамильцах и смене фамилии.

Поля:
- `school_year`.
- `student_id`: внутренний идентификатор из таблицы учеников. Формат требует подтверждения.
- `class_group`.
- `full_name`.
- `grade_number`: заполняется, если может отличаться от grade класса. Требует подтверждения.
- `is_active`.
- `source_row_order`.

Ограничения:
- уникальность по `school_year + student_id`;
- уникальность по `school_year + class_group + full_name` как страховка на период, пока ID не проставлены во всех строках источника.

### 4A.2 Изменения `FillTask`

Причина: заказчик задаёт окно рассылки, а не только дедлайн.

Добавить:
- `reminders_start_at`: дата начала рассылки.
- `reminders_end_at`: дата окончания рассылки.
- `reminder_time_local`: время ежедневного напоминания, по умолчанию `12:00`.

Поле `deadline_at` сохраняется как срок выполнения задачи, отдельный от окна рассылки.

### 4A.3 Изменения `TeacherSheetStatus`

Причина: таблица мониторинга должна показывать ошибки, первое заполнение, количество напоминаний и своевременность.

Добавить:
- `has_errors`.
- `error_count`.
- `errors_json`: коды и краткие описания ошибок значений из `validation/services.py`.
- `first_filled_at`: момент первого обнаруженного заполнения.
- `reminders_sent_count`: агрегат по журналу отправок.
- `is_on_time`: результат расчёта своевременности.

Ограничение: модель остаётся перезаписываемым снимком. Историю она не хранит, поэтому `first_filled_at` и `reminders_sent_count` рассчитываются из журнала, а не накапливаются в самой модели.

### 4A.4 Новая модель `SheetFillEvent`

Причина: KPI влияет на 13-ю зарплату, поэтому источник данных должен быть неизменяемым журналом, а не снимком.

Поля:
- `school_year`, `module`, `class_group`, `class_register`, `sheet_name`.
- `teacher_name`.
- `event_type`: `first_descriptor`, `first_criteria`, `first_grades`, `reminder_sent`, `validation_failed`, `completed`.
- `occurred_at`.
- `job_run`.
- `payload_json`.

Правила:
- записи только добавляются, изменение и удаление запрещены на уровне сервисного слоя;
- `TeacherSheetStatus` и таблица мониторинга строятся поверх этого журнала;
- существующий `notifications.NotificationEvent` остаётся журналом доставки, а `SheetFillEvent` связывает отправку с модулем и листом.

### 4A.5 Изменения `ReportArtifact`

- Привязка к ученику переходит с `student_name` на внешний ключ к `Student`.
- `student_name` сохраняется как денормализованная копия для читаемости отчётов.
- Уникальность переходит на `school_year + module + student + artifact_type`.

## 8. Риски и технические решения

### 8.1 Структура Google Sheets

Риск: без точных диапазонов/листов невозможно надежно заполнять и очищать class register.

Решение:
- до разработки генерации зафиксировать контракт шаблона;
- по возможности использовать именованные диапазоны или служебные маркеры;
- не полагаться только на номера строк, если структура может меняться.

### 8.2 Google API и права

Риск: система может не иметь доступа к папкам/файлам, хотя пользователь ожидает работу. Дополнительный риск: локально тестирование проходит через один Google-аккаунт, а на сервере операции будет выполнять другой аккаунт.

Решение:
- считать Google-учетку частью окружения, а не продуктовых данных;
- хранить в данных учебного года ссылки/ID папок и файлов, а credentials хранить только в env/секретах окружения;
- локально использовать OAuth-токен тестового аккаунта;
- на сервере использовать отдельный production OAuth-токен или service account;
- при переносе на сервер выдать новой учетке доступ к тем же Google Drive папкам и таблицам;
- при настройке года делать проверку доступности папок и шаблона;
- после смены credentials запускать полную проверку доступности сохраненных ссылок;
- завучу показывать понятную ошибку;
- администратору логировать точный Google API error.

### 8.3 Legacy DOCX генератор

Риск: генератор DOCX завязан на локальные файлы и текущие ожидания старого проекта.

Решение:
- оставить legacy adapter как отдельный слой;
- добавить слой скачивания/подготовки входных workbook;
- после генерации загружать DOCX в Google Drive;
- покрыть smoke-тестом реальные fixture workbook.

### 8.4 NotificationEvent сейчас используется шире, чем учителя

Риск: модель `NotificationEvent.teacher_name` сейчас применяется и для родительских email событий, что может путать отчеты.

Решение:
- либо аккуратно расширить модель полями `recipient_name`, `recipient_role`, `target`, сохранив обратную совместимость;
- либо создать отдельную модель `ParentReportDeliveryEvent`.

### 8.5 Массовые операции

Риск: создание файлов, конвертация PDF и отправка писем могут быть долгими.

Решение:
- все массовые операции запускать через `JobRun`;
- UI должен показывать `running/success/partial/failed`;
- не блокировать HTTP-запросы долгими операциями.

## 9. Definition of Done для MVP

MVP считается готовым, если:

- завуч может настроить учебный год без участия разработчика;
- система создает class register для выбранного модуля;
- система показывает проблемные классы и не блокирует валидные;
- мониторинг заполнения работает на платформе и в Google Sheet;
- Telegram-режимы отправляют стартовые сообщения и напоминания;
- DOCX генерируются по готовым классам;
- PDF создаются только после подтверждения вычитки;
- преподаватель получает сообщение с конкретными ошибками заполнения;
- мониторинг показывает ошибки, первое заполнение, количество напоминаний и своевременность;
- показатели KPI воспроизводимы и объяснимы;
- администратор видит технические логи;
- завуч не видит технические детали отказов доступа;
- есть smoke test полного цикла на тестовом учебном году.
